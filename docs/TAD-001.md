# 4. Principios arquitectónicos

CyberCBA utiliza una arquitectura de:

> **modular monolith**

No se utilizarán:

* microservicios;
* ECS complejo;
* service locators;
* dependency injection frameworks;
* event buses genéricos de terceros;
* reflection;
* scripting engines;
* arquitectura distribuida.

Principios:

1. simplicidad;
2. módulos pequeños;
3. ownership explícito;
4. lógica independiente de Raylib;
5. testabilidad;
6. dependencias unidireccionales;
7. estructuras custom;
8. mínimo acoplamiento;
9. cero abstracción especulativa.

La regla fundamental es:

```text
Domain/Game Logic MUST NOT depend on Raylib.
```


La lógica de:

* decisiones;
* progresión;
* misiones;
* relaciones;
* habilidades;
* condiciones;
* fail-forward;

debe poder compilarse y testearse sin abrir una ventana.

# 12. Semántica de ownership

Regla general:

> Un `T*` se considera **no-owner** salvo que el contrato del tipo indique explícitamente lo contrario.

El ownership dinámico debe estar encapsulado.

Ejemplo:

```text
Game
 ├── owns MainMenuState
 ├── owns MissionState
 ├── owns CombatState
 │
 └── currentState
       └── observer pointer
```

Ejemplo válido:

```cpp
class Game {
private:
    MainMenuState mainMenu_;
    MissionState mission_;
    CombatState combat_;

    IGameState* currentState_; // observer
};
```

Los objetos viven dentro de `Game`.

`currentState_` sólo observa uno de ellos.

No necesita allocation dinámica.

---

# 13. Uso de new/delete

`new` y `delete` MUST NOT aparecer arbitrariamente en gameplay.

Allocation dinámica se limita principalmente a:

* implementación de estructuras custom;
* wrappers de ownership;
* resource stores cuando sea inevitable.

Regla:

```text
quien crea con new
debe tener ownership explícito
y debe garantizar delete.
```

El código consumidor no destruye memoria que no posee.

---

# 14. Rule of Three / Five

Cualquier estructura que posea memoria dinámica debe definir correctamente según corresponda:

```cpp
~Type();

Type(const Type&);
Type& operator=(const Type&);

Type(Type&&);
Type& operator=(Type&&);
```

No se permite:

> shallow copy accidental de ownership.

Cuando copiar una estructura no tenga sentido:

```cpp
Type(const Type&) = delete;
Type& operator=(const Type&) = delete;
```

debe preferirse a una implementación incorrecta.

# 15. Estructuras custom del Vertical Slice

El Vertical Slice puede utilizar inicialmente cuatro ADTs fundamentales.

## DynamicArray<T>

Uso:

* listas de opciones;
* registros pequeños;
* recursos;
* datos variables.

Debe administrar su propia memoria.

---

## Queue<T>

Uso natural:

* eventos;
* diálogos pendientes;
* acciones diferidas.

---

## Stack<T>

Uso natural:

* navegación;
* overlays;
* historial limitado de estados.

---

## DirectedGraph

Uso:

* dependencias entre misiones;
* nodos del mapa central;
* desbloqueos.

No deben introducirse estructuras adicionales sin necesidad concreta.

# 16. State Machine

Los estados principales son:

```cpp
enum class GameStateId {
    MainMenu,
    CharacterSelection,
    Prologue,
    CentralMap,
    Mission,
    Puzzle,
    Combat,
    PostMission,
    Pause,
    Ending
};
```

Las transiciones deben ocurrir exclusivamente mediante una API explícita.

Ejemplo conceptual:

```cpp
game.transitionTo(GameStateId::Combat);
```

No debe modificarse el estado mediante flags dispersos como:

```cpp
isCombat = true;
showMap = false;
isMission = true;
```

---

# 17. Game loop

El loop de Raylib debe permanecer simple:

```text
capture input
      ↓
update game
      ↓
build visible state
      ↓
render
```

Conceptualmente:

```cpp
while (!WindowShouldClose()) {
    InputSnapshot input = inputAdapter.capture();

    game.update(input);

    BeginDrawing();

    renderer.draw(game);

    EndDrawing();
}
```

La lógica de gameplay ocurre en:

```cpp
game.update(...)
```

no en `renderer.draw()`.

---

# 18. Input

Raylib input debe convertirse primero en una representación independiente.

Ejemplo:

```cpp
struct InputSnapshot {
    bool confirm;
    bool cancel;
    bool moveUp;
    bool moveDown;
    bool moveLeft;
    bool moveRight;
};
```

El gameplay recibe:

```text
InputSnapshot
```

no llamadas directas a:

```cpp
IsKeyPressed(...)
GetMousePosition()
```

---

# 19. Rendering

El renderer observa estado.

No decide gameplay.

Incorrecto:

```cpp
if (player.health <= 0) {
    startGameOver();
}

DrawPlayer();
```

Correcto:

```cpp
game.update();

renderer.draw(game.view());
```

---

# 20. Assets

Debe existir un único responsable de cargar y descargar assets.

Conceptualmente:

```text
AssetStore
```

Responsabilidades:

* cargar;
* conservar handles;
* entregar recursos;
* descargar al finalizar.

No debe hacerse:

```cpp
LoadTexture(...)
```

desde múltiples sistemas de gameplay.

Para el Vertical Slice deben utilizarse IDs explícitos.

Ejemplo:

```cpp
enum class TextureId {
    NeoCbaMap,
    EmmaPortrait,
    MaggaPortrait,
    RefugeBackground
};
```

Esto evita necesitar mapas STL.

```text

```

utilizando Clang.

Flags:


* use-after-free;
* double-free;

* invalid memory access;
* comportamiento indefinido detectado;

* ownership es explícito;
* no utiliza contenedores STL prohibidos;
* no utiliza smart pointers estándar;
* respeta arquitectura;
* no deja TODO crítico;
* documentación relevante está actualizada;
* criterios de aceptación están satisfechos.

```text
tag vX.Y.Z
```

# 46. Coverage

Coverage puede generarse como métrica informativa.

Durante el Vertical Slice:

> no existe un porcentaje global obligatorio.

Una cobertura alta no reemplaza tests significativos.

La regla obligatoria es:

> nueva lógica determinista importante → nuevos tests.

---

# 47. Error handling

Los errores esperables deben tratarse explícitamente.

Ejemplos:

* asset faltante;
* misión inexistente;
* transition inválida;
* recurso agotado.

No ocultar errores silenciosamente.

Debug builds deben utilizar:

```cpp
assert(...)
```

para invariantes internas cuando corresponda.

Los errores recuperables no deben convertirse indiscriminadamente en `assert`.

---

# 48. Logging

Debe existir una capa mínima de logging.

Niveles:

```text
DEBUG
INFO
WARNING
ERROR
```

No utilizar `printf()` disperso como estrategia de diagnóstico permanente.

El adapter puede utilizar las capacidades de Raylib cuando corresponda, pero gameplay no debe depender de ellas.

---

# 49. Diseño de APIs

Preferir:

```cpp
combat.resolveAction(action);
```

sobre:

```cpp
combat.doEverything(
    player,
    enemies,
    textures,
    sounds,
    window,
    input,
    mission,
    config
);
```

APIs pequeñas.

Dependencias explícitas.

---

# 50. Funciones

Una función debería poseer:

> una responsabilidad observable.

Evitar funciones gigantes como:

```cpp
updateGame()
```

de cientos de líneas.

Preferir:

```cpp
updateMission()
resolveChoice()
applyCombatAction()
advanceDialogue()
```

---

# 51. Managers

El sufijo:

```text
Manager
```

no está prohibido.

Pero requiere una responsabilidad específica.

Aceptable:

```text
AssetManager
```

si realmente administra lifecycle de assets.

No aceptable:

```text
GameManager
```

conteniendo:

* gameplay;
* rendering;
* input;
* sonido;
* save;
* misiones;
* combate.

---

# 52. Global state

Prohibido como arquitectura:

```cpp
extern Game* gGame;
extern Player player;
static Mission currentMission;
```

Estado debe vivir dentro de objetos propietarios.

Constantes compile-time globales son aceptables cuando corresponda.

---

# 53. Persistencia

Persistencia completa no forma parte inicialmente del Vertical Slice salvo que `VS-001` la requiera.

Si se necesita durante el slice:

> guardar sólo el mínimo estado requerido.

No implementar un framework de serialización genérico anticipadamente.

---

# 54. Seguridad de assets

Una textura o sonido debe descargarse exactamente una vez.

Lifecycle:

```text
AssetStore constructor/init
       ↓
load
       ↓
runtime
       ↓
shutdown/destructor
       ↓
unload
```

Los consumidores reciben referencias/handles observadores.

No poseen el recurso.

---

# 55. Performance

Objetivo inicial:

```text
60 FPS
```

pero la arquitectura no debe sacrificar claridad por micro-optimizaciones prematuras.

Optimización se realiza solamente ante:

* profiling;
* evidencia;
* problema observable.

El juego posee scope pequeño y gameplay predominantemente discreto.

# 60. Política NOLINT

`NOLINT` sólo puede utilizarse cuando:

1. el warning es entendido;
2. la implementación es deliberada;
3. existe justificación local.

Ejemplo:

```cpp
// NOLINTNEXTLINE(check-name) — reason: ...
```

No utilizar:

```cpp
// NOLINT
```

como mecanismo genérico para "hacer pasar clang-tidy".

---

# 61. Política de TODO

Todo TODO debe explicar:

```text
qué falta
por qué falta
milestone asociado
```

Ejemplo:

```cpp
// TODO(VS-002): Replace temporary lookup with mission graph traversal.
```

Evitar:

```cpp
// TODO fix
```
