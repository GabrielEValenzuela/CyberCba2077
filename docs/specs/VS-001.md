# 0. Cómo leer este documento

Este documento fija, sin ambigüedad, todo lo que debe implementarse para el Vertical Slice. Ante cualquier conflicto se aplica la jerarquía definida en TAD §2 (GPD > TAD > VS-001 > ADR > tests > código).

Elementos marcados `[VS-ALIAS]` son identificadores usados **solo dentro del Vertical Slice** para poder escribir diálogo concreto sin fijar nombres canónicos que el GPD marca como `TBD` (ej. nombre del líder oculto). No deben tratarse como canon narrativo definitivo — son placeholders explícitamente reversibles.

---

# 1. Alcance funcional

Incluye:

* Main Menu → Character Selection → Prologue → Central Map → Mission 1 → Post-Mission → Central Map.
* Elección Emma/Magga con diferencias reales de diálogo/resolución.
* Un desafío de hacking/puzzle.
* Un combate táctico.
* Al menos una decisión narrativa con dos vías.
* Un escenario de fail-forward.
* Progresión: 1 punto de habilidad al cerrar la misión.

No incluye (fuera de scope para VS-001):

* Acto I completo (misiones 2–3 del Acto I quedan fuera);
* Acto II, Acto III;
* pantalla de guardado persistente (ver §11);
* mapa parcialmente abierto (eso es Acto II).

---

# 2. Game states usados en VS-001

De TAD §16, el VS utiliza:

```text
MainMenu → CharacterSelection → Prologue → CentralMap → Mission → Puzzle → Combat → PostMission
```

`Pause` y `Ending` deben existir como estados válidos en el enum (`GameStateId`) pero no requieren contenido narrativo propio en VS-001; `Pause` solo necesita poder pausar/reanudar sin crashear.

# 3. Prólogo — "La Extracción de Datos" (VS-ALIAS del nombre de misión)

Contexto: Emma y Magga siguen siendo pareja y compañeros operativos de Las Luciérnagas. Objetivo de la operación: extraer un archivo comprometedor desde un servidor de La RED en una instalación de vigilancia de NeoCBA (distrito `[VS-ALIAS: Distrito Bajo]`).

El operativo capturado durante esta misión es un miembro del equipo, identificado en VS-001 como `[VS-ALIAS: "Fantasma"]` — es quien luego el GPD revela como el verdadero líder oculto de Las Luciérnagas (nombre canónico TBD, no se fija aquí).

## 3.1 Escena P1 — Briefing

**Tipo:** diálogo lineal sobre fondo estático (refugio de Las Luciérnagas).

Personajes presentes: Emma, Magga, Fantasma (retrato + sprite).

Contenido:

* Fantasma explica el objetivo: acceder al servidor de vigilancia, extraer el archivo `EXPEDIENTE-array`, salir sin ser detectados.
* Se establece el vínculo Emma/Magga como pareja mediante 2–3 líneas de diálogo (tono, no exposición forzada).
* No hay decisiones. Termina con transición a P2.

Salida: `GameStateId::Mission` (escena de misión, sub-escena "instalación exterior").

## 3.2 Escena P2 — Acceso a la instalación

**Tipo:** escena de misión con interacción + puzzle.

* Fondo: exterior de instalación de vigilancia.
* Elemento interactivo: panel de acceso eléctrico.
* Puzzle: **familia "Redirección de energía"** (ver §6.1), dificultad baja (3 nodos, sin límite de movimientos).
* Éxito: acceso abierto, continúa a P3 sin penalidad.
* Fallo (agotar intentos definidos en §6.1): se dispara una alarma silenciosa; esto se registra como flag `alarmTriggered = true` y afecta el combate de P4 (fail-forward, ver §3.5).

Recurso disponible en esta escena: `EMP_CHARGE` (1 unidad) — puede usarse para forzar el panel evitando el puzzle. Si se usa, el puzzle se salta automáticamente con éxito, pero el recurso se consume y no está disponible en escenas posteriores.

## 3.3 Escena P3 — Sala de servidores

**Tipo:** diálogo + decisión narrativa (la decisión central del Vertical Slice, GPD §5.1/§27).

* Emma detecta que el archivo objetivo está protegido con una capa de cifrado adicional no prevista.
* Diálogo entre Emma y Magga expone el conflicto del GPD §27:
  * Emma: quiere quedarse y forzar el descifrado (más tiempo = más riesgo, pero información completa).
  * Magga: quiere extraer lo que ya se tiene y evacuar (menos riesgo, información parcial).

### Decisión (jugador controla al personaje elegido en Character Selection)

**Si el jugador es Emma:**

* Opción A — "Quedarme y terminar el descifrado" → puzzle adicional **familia "Descifrado de transmisión"** (ver §6.2), dificultad media (4 símbolos, 45s límite de tiempo simulado por turnos, no reloj real).
  * Éxito: información completa (`intelComplete = true`), pero incrementa el riesgo de la escena de combate (aparecen 1 guardia adicional en P4).
  * Fallo: información parcial (`intelComplete = false`), igualmente incrementa el riesgo (mismo guardia adicional, porque el tiempo se perdió igual).
* Opción B — "Escuchar a Magga y evacuar ahora" → sin puzzle adicional. `intelComplete = false`. Combate de P4 sin guardia adicional.

**Si el jugador es Magga:**

* Opción A — "Confiar en Emma y cubrir la posición" → mismo puzzle "Descifrado de transmisión" resuelto por Emma (NPC), pero el jugador (Magga) debe superar una sub-decisión táctica: elegir posición de cobertura (afecta recursos de combate en P4: +1 uso de `COVER_BONUS` si se elige bien, ninguno si se elige mal — la elección correcta se determina por una pista de Percepción visible en pantalla, no oculta).
  * Éxito de Emma: `intelComplete = true` + guardia adicional (igual que arriba).
* Opción B — "Ordenar evacuación inmediata" → `intelComplete = false`, sin guardia adicional.

Ambas vías convergen: la escena termina y se pasa a P4 (combate), con el estado `alarmTriggered`, `intelComplete` y `guardCountModifier` (0 o +1) fijados según lo anterior.

Esto satisface GPD §5.1 (≥2 vías de resolución por personaje) y §5.3 (consecuencias controladas, no exponenciales).

## 3.4 Escena P4 — Combate: Retirada bajo fuego

**Tipo:** `GameStateId::Combat` (ver §7).

* Enemigos base: 2 guardias de La RED. Si `guardCountModifier == 1`: 3 guardias.
* Si `alarmTriggered == true`: los guardias comienzan en estado "alerta" (ventaja inicial para el enemigo: un turno de ataque antes de que el jugador pueda actuar).
* Objetivo de combate: reducir la resistencia del grupo enemigo por debajo del umbral de retirada, o sobrevivir el número de rondas definido, permitiendo la extracción.

### Resultado

* **Victoria:** el equipo escapa. Continúa a P5.
* **Derrota / fail-forward:** ver §3.5. El equipo igual escapa (no hay Game Over en el prólogo), pero con consecuencias narrativas peores.

## 3.5 Fail-forward del prólogo

Definición concreta de GPD §5.4 para esta misión:

* Si el jugador **pierde el combate de P4** (resistencia del equipo llega a 0 antes de vencer a los enemigos):
  * Fantasma resulta herido cubriendo la retirada y es **capturado** por La RED al quedar rezagado.
  * Flag: `missionOutcome = Captured`.
* Si el jugador **gana el combate de P4**:
  * Durante la extracción, La RED corta la única ruta de escape segura. Fantasma se separa del grupo para activar una ruta alternativa y es capturado en el proceso de todas formas — el prólogo (GPD §28) exige que la operación termine en desastre con la desaparición de un miembro, independientemente del resultado táctico del jugador.
  * Flag: `missionOutcome = Success` o `Captured` según combate, pero **la captura de Fantasma ocurre en ambos casos** vía narrativa (ver GPD §27–28: "la decisión termina en desastre" es un punto fijo de la trama, no una rama del jugador).

Esto preserva GPD §27–28 como canon fijo (Fantasma es capturado siempre) mientras el combate del jugador sí modifica **cómo** ocurre y **qué tan grave** es (P5 varía el tono y una línea de diálogo según `missionOutcome`), cumpliendo fail-forward sin bloquear progreso.

## 3.6 Escena P5 — Consecuencia y ruptura

**Tipo:** diálogo lineal, sin decisiones.

* Escena corta: el equipo confirma la captura de Fantasma.
* Emma y Magga se culpan mutuamente (GPD §29), 4–6 líneas de diálogo alternando reproches y dolor compartido.
* Termina con la decisión narrativa fija de separarse (no es una elección del jugador — es un beat de trama establecido por GPD §29).
* Transición: salto temporal (pantalla de texto simple: "Tres meses después" `[VS-ALIAS duración]`, GPD §30 marca duración exacta como TBD; VS-001 fija 3 meses solo como valor de implementación reversible).

## 3.7 Escena P6 — El mensaje cifrado

**Tipo:** diálogo lineal, específico del personaje elegido (GPD §31).

* El protagonista seleccionado recibe un mensaje cifrado anónimo.
* Contenido (idéntico en esencia para Emma/Magga, con tono ajustado a su voz): evidencia de que la misión fallida tuvo una intervención interna ("alguien abrió la puerta desde adentro").
* No hay puzzle aquí — descifrar el mensaje es el gancho narrativo de la Misión 1, no de esta escena.
* Termina la transición: `GameStateId::CentralMap`.

# 5. Misión 1 — "Rastro Frío"

Contexto: el protagonista sigue el primer rastro del mensaje cifrado hasta un contacto de Las Luciérnagas que puede confirmar si Fantasma sigue con vida.

## 5.1 Escena M1 — Llegada y contacto

**Tipo:** diálogo + interacción.

* Fondo: refugio secundario (reutiliza asset de refugio del prólogo con iluminación distinta, GPD §46).
* NPC: contacto `[VS-ALIAS: "Ratón"]`, desconfiado.
* El jugador debe convencer al contacto de cooperar. Aquí se aplica la diferencia de personaje (GPD §9):
  * **Emma:** puede ofrecer acceso a un canal cifrado como prueba de buena fe (usa Hackeo/Criptografía narrativamente, sin puzzle mecánico adicional aquí).
  * **Magga:** puede usar Intimidación/Persuasión directa para presionar cooperación.
* Ambas vías llevan al mismo resultado funcional (Ratón coopera) pero con líneas de diálogo y tono distintos — esto satisface GPD §5.1 sin bifurcar el flujo de misión.

## 5.2 Escena M2 — Interferencia de vigilancia (Puzzle)

**Tipo:** `GameStateId::Puzzle`.

* Ratón necesita que el jugador interfiera una cámara de vigilancia cercana para hablar con seguridad.
* Puzzle: familia **"Interferencia de vigilancia"** (ver §6.3), dificultad baja-media.
* Éxito: Ratón entrega la pista (Fantasma fue visto con vida, trasladado a una instalación de La RED).
* Fallo: se activa una ronda de guardia; el jugador debe resolver el puzzle una segunda vez con un intento menos disponible (fail-forward local, no bloquea progreso — ver TAD §32 "puzzle logic" debe ser testeable).

## 5.3 Escena M3 — Emboscada (Combate)

**Tipo:** `GameStateId::Combat`.

* Al salir del refugio, guardias de La RED que seguían a Ratón (o al jugador, si M2 falló) atacan.
* Enemigos: 2 guardias base, mismo sistema de combate que P4 reutilizado (GPD §5.5 producción reutilizable).
* Victoria o derrota-con-fail-forward (el jugador siempre escapa; una derrota táctica implica perder el recurso `EMP_CHARGE` restante o sufrir daño narrativo menor, sin bloquear la misión).

## 5.4 Escena M4 — Cierre de misión

**Tipo:** diálogo lineal.

* Confirmación narrativa: Fantasma está vivo y siendo trasladado.
* Gancho de cierre del VS: se establece que el protagonista debe encontrar apoyo para el rescate — esto es la transición hacia el resto del Acto I (fuera de scope de VS-001, solo se menciona, no se implementa).
* Transición: `GameStateId::PostMission`.

# 6. Puzzles concretos (familias reutilizables, GPD §7.3/§17)

VS-001 utiliza **3 de las 3–4 familias** permitidas por el GPD. Todas comparten la misma interfaz de `PuzzleSystem` (TAD §65); solo cambian datos de configuración, no código.

## 6.1 Familia: Redirección de energía

* Representación: N nodos conectados, el jugador rota conectores para formar un camino válido entre origen y destino.
* Estructura de datos: `DirectedGraph` (nodos = conectores, aristas = conexiones válidas actuales).
* Parámetros de dificultad: cantidad de nodos, cantidad de movimientos permitidos.
* Usado en: P2 (3 nodos, movimientos ilimitados).

## 6.2 Familia: Descifrado de transmisión

* Representación: secuencia de símbolos que debe reordenarse/emparejarse según una regla mostrada parcialmente (información incompleta, GPD §7.3).
* Estructura de datos: `DynamicArray<Symbol>` para la secuencia actual + `Stack<Symbol>` para deshacer movimientos.
* Parámetros de dificultad: cantidad de símbolos, cantidad de turnos disponibles.
* Usado en: P3 rama Emma "Opción A" (4 símbolos, 6 turnos).

## 6.3 Familia: Interferencia de vigilancia

* Representación: cola de eventos de vigilancia (rondas de cámara) que el jugador debe "vaciar"/neutralizar en el orden correcto antes de que se agote el límite de intentos.
* Estructura de datos: `Queue<SurveillanceEvent>`.
* Parámetros de dificultad: cantidad de eventos en cola, intentos disponibles.
* Usado en: M2 (3 eventos, 3 intentos; en el retry por fallo: 3 eventos, 2 intentos).

No se introduce una cuarta familia en VS-001; queda reservada por el GPD para producción futura si se necesita.

# 7. Combate táctico concreto

## 7.1 Modelo

* Sin grilla (GPD §16).
* Cada lado (jugador/enemigos) tiene una **resistencia** numérica agregada (no HP individual por unidad en VS-001 — simplificación deliberada y reversible para mantener el combate en 2–5 minutos).
* El combate avanza por rondas. En cada ronda el jugador elige **una acción**; los enemigos responden según una regla determinista simple (no IA compleja).

## 7.2 Acciones disponibles (GPD §16)

Comunes a ambos personajes:

* `ATACAR` — daño base a la resistencia enemiga.
* `CUBRIRSE` — reduce el daño recibido la próxima ronda enemiga.
* `RETIRARSE` — termina el combate con resultado "escape parcial" (equivalente a derrota táctica pero sin fail-forward severo; disponible solo después de la ronda 2).

Exclusivas:

* Magga: `MANIOBRA` — daño alto con riesgo de exponerse (recibe más daño la ronda siguiente si no se sigue de `CUBRIRSE`). Refleja ventaja de combate directo (GPD §16 "Magga debe poseer ventajas evidentes en combate").
* Emma: `USAR_RECURSO` (`EMP_CHARGE` si está disponible) — daño en área que reduce resistencia de todos los enemigos simultáneamente, pero consume el recurso. Si Emma no tiene el recurso disponible, la acción no aparece como opción válida (regla: acciones dependen de recursos, GPD §16).

## 7.3 Resolución determinista

* Daño base `ATACAR`: 10.
* Daño `MANIOBRA` (Magga): 16, pero marca `exposed = true` si no se sigue con `CUBRIRSE`.
* Daño `USAR_RECURSO` (Emma, EMP): 8 a cada enemigo activo.
* `CUBRIRSE`: reduce el próximo daño recibido en 50%.
* Resistencia inicial: jugador 30 (+`COVER_BONUS` +10 si aplica desde P3); guardia individual 15.
* Enemigos atacan automáticamente cada ronda por 8 de daño al total del jugador (12 si `alarmTriggered`), salvo que el jugador esté cubierto.

Estos números son valores de implementación del Vertical Slice (GPD §76 marca "reglas matemáticas exactas de combate" como TBD a nivel de producto general); quedan fijados aquí como concretos y testeables para VS-001, ajustables sin romper arquitectura.

## 7.4 Condición de fin de combate

* Victoria: resistencia enemiga total ≤ 0.
* Derrota táctica (fail-forward, no Game Over): resistencia del jugador ≤ 0, o el jugador elige `RETIRARSE`.
* No existe Game Over en VS-001. Todo combate perdido dispara la rama de fail-forward narrativo correspondiente descrita en cada escena (§3.5, §5.3).

# 9. Progresión (post-misión)

Al cerrar el Prólogo y al cerrar Misión 1, se ejecuta el flujo de GPD §7.5:

1. Mostrar consecuencias inmediatas (ya cubierto por P5/M4).
2. Escena narrativa breve (ya cubierta).
3. Otorgar 1 punto de habilidad.
4. Pantalla de mejora: el jugador elige **una** habilidad de Nivel I entre las disponibles para su personaje (5 comunes + 5 exclusivas, GPD §11), incrementándola a Nivel II si ya estaba en Nivel I (VS-001 no exige lógica de Nivel III — alcanzable pero no forzada en este slice).
5. Retorno a `CentralMap`.

La lista completa de 15 habilidades y sus 3 niveles debe existir como datos (`SkillDefinition`), pero solo los efectos mecánicos de las habilidades **usadas explícitamente en el prólogo y Misión 1** (Persuasión/Intimidación en M1, Percepción en P3 rama Magga) requieren lógica funcional en VS-001. El resto puede existir como datos seleccionables sin efecto mecánico adicional todavía (marcar con TODO(VS-002) según TAD §61).

# 9.5 NPCs — comportamiento mediante Strategy

Los NPCs de VS-001 (Fantasma, Ratón, guardias de La RED) no deben codificar su comportamiento mediante `if/else` dispersos según el protagonista activo. Se utiliza el patrón **Strategy** (composición, GPD §64/§80) para las decisiones de NPC que varían por escena o por personaje jugador.

## 9.5.1 `IPersuasionStrategy`

Usado en M1 (§5.1) para resolver si Ratón coopera.

```cpp
class IPersuasionStrategy {
public:
    virtual ~IPersuasionStrategy() = default;
    virtual bool attempt(const CampaignState& state) const = 0;
    virtual const DialogueLine* resultLines() const = 0;
};

class HackerProofStrategy : public IPersuasionStrategy { /* Emma: Hackeo/Criptografía */ };
class IntimidationStrategy : public IPersuasionStrategy { /* Magga: Intimidación */ };
```

`NpcContact` (Ratón) posee una referencia observadora a la estrategia activa, seleccionada por `MissionSystem` según `CampaignState::player` al entrar a M1. No posee la estrategia (las instancias de estrategia son propiedad de la definición de escena/`MissionSystem`, con lifetime igual o mayor al de la escena).

## 9.5.2 `IGuardBehaviorStrategy`

Usado por los guardias en combate (P4/M3) para decidir su acción por ronda (§7.3). Aun cuando VS-001 solo requiere una regla determinista, debe expresarse como estrategia para permitir variantes futuras (guardia en alerta vs. guardia normal) sin condicionales dispersos:

```cpp
class IGuardBehaviorStrategy {
public:
    virtual ~IGuardBehaviorStrategy() = default;
    virtual CombatAction decideAction(const CombatState& state) const = 0;
};

class StandardGuardStrategy : public IGuardBehaviorStrategy { /* daño base 8 */ };
class AlertedGuardStrategy : public IGuardBehaviorStrategy { /* daño 12, usado si alarmTriggered */ };
```

`CombatSystem` selecciona la estrategia de guardia una vez al iniciar el combate según `alarmTriggered`, no por-ronda.

## 9.5.3 Ownership

Las estrategias concretas son objetos sin estado mutable propio (comportamiento puro sobre el estado recibido por parámetro). Pueden vivir como instancias estáticas/miembros de `MissionSystem`/`CombatSystem` (owner), expuestas a NPCs y a `CombatSystem` como punteros observadores. No se crean con `new` por instancia de NPC.

# 11. Persistencia

Por TAD §53, VS-001 no requiere save/load a disco. El estado de campaña (elección de personaje, flags: `alarmTriggered`, `intelComplete`, `missionOutcome`, recursos, habilidades) vive en memoria durante la sesión, dentro de `CampaignState`, propiedad de `Game`. Cerrar la aplicación descarta el progreso. Esto es aceptable y explícito para VS-001.

## 12.2 `cybercba/structures` — API pública únicamente (fuera de scope de implementación)

```text
DynamicArray<T>
Queue<T>
Stack<T>
DirectedGraph<T>   (nodos = escenas/misión; conectores del puzzle 6.1)
```

**Decisión de scope (reemplaza implementación previa):** la implementación de estas cuatro estructuras **no es responsabilidad del agente de IA ni de esta pasada de trabajo**. Se trata de un ejercicio de estructuras de datos reservado a los estudiantes/desarrolladores del equipo (GPD §55/§2 "estudiantes deberán implementar... estructuras de datos propias").

Para esta pasada:

* Se define únicamente el **header público** (`include/cybercba/structures/*.hpp`) de cada estructura: firmas de métodos, contrato documentado (precondiciones/invariantes, TAD §5 principio 5), reglas de ownership (rule of three/five declarada en la firma, TAD §14), sin cuerpo de implementación (declaración únicamente o `// TODO(students): implement`).
* Los sistemas de `cybercba_core` que dependen de ellas (`PuzzleSystem` con `DirectedGraph`/`DynamicArray`/`Stack`, `MissionSystem` con `Queue`) se escriben contra esa API pública y **no compilarán a ejecutable enlazable** hasta que la implementación exista — esto es esperado y aceptable en esta pasada.
* No se agregan tests de estructura (TAD §33) hasta que exista implementación real; agregar tests contra un stub sin cuerpo no aporta valor.
* Ownership documentado igual aplica desde ya (TAD §12/§54): cada estructura administra su propia memoria; consumidores usan solo la API pública, nunca nodos internos — esto queda fijado en el contrato del header para que la implementación posterior no pueda romperlo sin violar la API.

## 12.3 `cybercba_raylib`

```text
InputAdapter   — traduce Raylib input a InputSnapshot (TAD §18)
Renderer        — dibuja según CampaignState/estado de escena actual (observador, TAD §19)
AssetStore       — TextureId/PortraitId/AudioId enum-driven (TAD §20)
AudioAdapter     — reproduce feedback, no decide reglas
```

## 12.4 `cybercba_app`

```text
main.cpp — composition root: construye Game, InputAdapter, Renderer, AssetStore, AudioAdapter; corre el loop (TAD §17)
```

**Nota de scope (§12.2):** dado que las 4 estructuras custom quedan reservadas a implementación futura por los estudiantes, `PuzzleSystem` (las 3 familias) es lo único que no enlaza a un binario ejecutable en esta pasada — está aislado en su propio target (`cybercba_core_puzzle`, un *object library*) precisamente para que el resto del árbol (core, raylib platform, app, tests) compile, enlace y corra normalmente sin esperar esa implementación.

* [x] `cybercba_core` compila y enlaza (estático); `cybercba_core_puzzle` (PuzzleSystem) compila como object library y queda sin enlazar a un ejecutable hasta que existan los cuerpos de `structures/`.
* [x] `cybercba_app` compila, enlaza contra raylib (vía vcpkg, ver ADR-002) y ejecuta en desktop sin crash (ventana real, ciclo `update`/`draw` verificado manualmente).
